# Frontend–Backend 계약 대조 기록

확인일: 2026-09-17  
대상: `dib-backend` `develop` 커밋 `39ecae71f972ca10883599b821932d6c980f2b0d`

이 문서는 Android 구현 중 발견한 실제 백엔드 코드와 확정 제품 정책의 차이를 기록한다. 백엔드 저장소는 읽기만 했으며 변경하지 않았다.

## 프론트에서 호환 처리한 조회 계약

| 기능 | 백엔드 구현 | 프론트 처리 |
|---|---|---|
| 카테고리 조회 | `GET /api/v1/categories`, `data`가 배열 | 배열과 목표 `items` 객체를 모두 해석 |
| 상품 상세 | `GET /api/v1/products/{productId}`, `data`가 상품 객체 | 직접 객체와 목표 `product` 객체를 모두 해석 |
| 내 상품 | `GET /api/v1/products/members/me`, `data`가 배열 | 실제 경로 사용, 배열·페이지 응답 모두 해석 |
| 상품 검색 | `GET /api/v1/products/search?keyword=...`, `data`가 배열 | 실제 `keyword` 사용, 배열·페이지 응답 모두 해석 |
| 상품 상태 | 목록 응답 필드가 `productStatus` | 목표 `status`와 `productStatus`를 모두 지원 |
| 경매 목록 | `GET /api/v1/auctions`, `data`가 배열 | 배열과 목표 페이지 응답을 모두 해석하고 상태·일반/Live·가격을 로컬 보정 |
| 경매 추천 | `GET /api/v1/auctions/recommendation`, `data`가 배열 | 배열을 일반 경매 추천으로 해석하고 목표 추천 객체도 지원 |
| 경매 시간 | 날짜가 오프셋 없는 `LocalDateTime`일 수 있음 | ISO Instant와 기기 시간대 LocalDateTime을 모두 해석 |
| 찜 | 상품 기준 명령과 상품 ID 배열 조회 | 카드에 `productId`를 유지하고 상품 ID로 등록·해제, 찜 상품을 경매 목록과 결합 |

## 정책 또는 기능 구현이 먼저 필요한 항목

### 고정 보증금 1,000원

- 확정 정책: 입찰자는 첫 입찰 전, 판매자는 경매 시작 전에 각각 1,000원을 결제한다.
- 백엔드에는 보증금 도메인, 테이블, 조회·준비·승인·환불 API가 없다.
- `BidTxServiceImpl`은 보증금을 확인하지 않고 입찰을 저장한다.
- `AuctionCommandServiceImpl.startAuction`은 보증금을 확인하지 않고 경매를 즉시 시작한다.
- 프론트의 `/auctions/{id}/deposits/prepare`, `/bid-deposits/{id}/confirm`, `/auctions/{id}/deposits/me`는 현재 백엔드에 존재하지 않는다.

보증금 계약이 생기기 전에는 실제 결제 성공으로 보이는 우회 동작을 추가하지 않는다.

### 상품 등록과 경매 등록의 분리

- 확정 정책: 상품 등록 후 검수 대기 상태가 되고, 승인된 상품을 선택해 일반 경매 또는 Live 경매를 별도로 등록한다.
- 현재 백엔드 `ProductCommandServiceImpl.create`는 상품 등록 요청에서 `startPrice`, `auctionTime`을 받아 `PENDING` 경매도 동시에 생성한다.
- Android는 확정 정책에 따라 상품 등록과 경매 등록을 분리해 둔다.
- 백엔드가 분리되기 전까지 상품 등록 명령은 실제 연동 완료로 판단하지 않는다.

### 상품 이미지 등록·수정

- 백엔드 등록 파트 이름은 `request`, 프론트는 목표 명세에 따라 `product`와 `imageTypes`를 보낸다.
- 백엔드는 대표 이미지 타입을 받지 않으며 첫 이미지를 문자열로 저장한다.
- 백엔드 수정은 JSON만 받고 교체 이미지 업로드를 지원하지 않는다.

### Live

- 프론트에 필요한 피드, 내 방송, 상품 편성, 송출 준비, 방송 시작·종료, 상품 경매 시작 API가 현재 백엔드에 없다.
- 백엔드 Live 채팅 REST 경로는 `/chats`, 목표 프론트 계약은 `/messages`다.
- LiveKit 토큰 응답은 `data`가 아니라 `response` 키를 사용한다.

### 경매 목록과 추천의 서버 기능

- 백엔드 경매 목록과 추천 배열은 프론트가 호환 처리한다.
- 검색·카테고리 필터·커서 페이지 파라미터는 백엔드에 구현되지 않았다.
- 프론트는 응답에 포함된 필드로 상태·일반/Live·가격을 임시 보정하지만, 정확한 카테고리 필터와 다음 페이지 로딩은 백엔드 구현이 필요하다.

## 비교 결과 일치하는 주요 영역

- 이메일 인증·회원가입·로그인·토큰 재발급·로그아웃 경로
- 배송지 등록·수정·삭제·조회 경로
- 주문 목록·상세·구매 확정·배송 조회·등록 경로
- 결제수단 조회·등록·삭제 및 주문 결제 재시도 경로
- 알림 목록·읽음·전체 읽음 경로
- 문의 등록·목록·상세 경로
- 정산 계좌와 정산 내역 경로

경로가 일치하더라도 응답 DTO와 인증 헤더는 통합 테스트에서 별도로 확인해야 한다.
